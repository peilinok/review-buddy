# Review Buddy

## Overview

Most review interfaces assume the reviewer can reconstruct intent, architecture, and risk directly from a giant diff. In practice, that breaks down fast — especially for large changes, mixed PRs, unfamiliar modules, and edits generated by coding agents like Claude Code or Codex.

Review Buddy turns code review into a guided, context-aware process. Instead of dumping one giant summary, it progressively:

1. frames the review target,
2. pulls in the missing surrounding context,
3. decomposes the change into meaningful review chunks,
4. applies the right review lenses to each chunk,
5. and consolidates findings into a clear final verdict.

This skill is explicitly **human-in-the-loop**. The AI should not try to replace the reviewer with a one-shot judgment. It should help the reviewer build understanding, maintain pacing, and inspect each part of the change with the right standards.

**Core principle:** do not judge code before understanding change intent, surrounding context, and risk boundaries.

---

## When to Use

Use this skill when:

- reviewing a pull request and the native diff view is too large or too flat
- reviewing local changes before push and you want more than a raw diff walkthrough
- reviewing changes made by Claude Code, Codex, or another coding agent
- reviewing code in an unfamiliar subsystem
- reviewing a mixed PR that touches multiple modules or abstraction layers
- you want AI to progressively guide the review instead of dumping a one-shot verdict
- you want the human reviewer to retain final judgment while using AI for context gathering and structured reasoning

Especially useful when:

- the diff is large
- the review target spans multiple files or layers
- the PR description is weak or incomplete
- the reviewer lacks local context
- the code looks polished but may hide shallow understanding or unsafe assumptions

---

## Don’t Use For

Skip or simplify this workflow when:

- the change is trivial and self-evident (formatting-only, typo-only, one-line config fix)
- the goal is purely mechanical verification
- the user explicitly wants a fast one-shot summary
- a very urgent hotfix only allows a minimal smoke review

Use `github-code-review` alongside this skill for GitHub-specific operations like checkout, inline review comments, approval, and request-changes flows.

Use `requesting-code-review` for pre-commit verification of your own changes with automated checks and independent reviewer/fix loops.

# Review Modes

Choose the lightest mode that still preserves reviewer confidence.

## 1. Quick Triage

Use for small diffs or first-pass screening.

Output:

- change type
- scope summary
- changed file groups
- risk hotspots
- suggested review order

Do **not** jump to deep findings yet. This mode is for orientation.

## 2. Standard Guided Review

Default mode.

Output:

- review brief
- context bootstrap
- change decomposition into chunks
- guided chunk-by-chunk review
- consolidated summary with blocking / non-blocking findings

Use this for most real PRs and local change reviews.

## 3. Deep Risk Review

Use for security-sensitive, correctness-critical, migration-heavy, or high-blast-radius changes.

Additional expectations:

- broader context gathering
- stronger contract checking
- explicit failure-mode analysis
- test adequacy analysis
- rollback and observability scrutiny

# Review Workflow

Always follow these phases in order. Do not skip to detailed judgment before the earlier phases are complete.

## Phase 0 — Frame the Review

First identify exactly what is being reviewed:

- local unstaged changes
- staged changes
- commit range
- branch diff
- GitHub PR

Collect the review envelope:

- title / PR title if available
- description / PR body / commit message cluster
- changed files
- diff stats
- test or CI signal if available
- base branch

### Required Output: Review Brief

Produce:

- **Change type** — bugfix / feature / refactor / infra / cleanup / mixed
- **Scope** — file count, modules touched, insertions/deletions if known
- **Probable intent** — what the change seems to be trying to do
- **Risk hotspots** — where reviewer attention should focus
- **Suggested review order** — what to inspect first, second, third
- **Confidence in inferred intent** — high / medium / low

### Rules

- If the written description is missing, infer intent cautiously from diff, filenames, tests, and symbols.
- Explicitly label inference as inference.
- Do not claim bugs or quality verdicts yet.

---

## Phase 1 — Bootstrap Context

The diff alone is not enough. Pull in the smallest surrounding context that makes intelligent review possible.

Read or inspect, as appropriate:

- the changed files themselves
- nearby unchanged code around modified regions
- interfaces, types, schemas, and contracts touched by the change
- direct callers and callees of modified functions
- tests related to the changed behavior
- relevant docs, ADRs, README sections, or explanatory comments
- PR description, linked issue context, or commit history when available

### Context Questions

Before chunking the review, answer:

- What subsystem or domain does this code belong to?
- What behavior existed before the change?
- What new assumption is being introduced?
- Which codepaths are user-facing, stateful, security-sensitive, or failure-prone?
- Which tests currently anchor the intended behavior?

### Context Retrieval Heuristics

Prefer this order when time is limited:

1. tests that cover the changed behavior
2. direct callers and callees
3. interface / type / schema definitions
4. neighboring unchanged code
5. docs / ADR / README
6. git history / blame / earlier commits in the PR

### Required Output: Context Cards

For each major area touched, summarize:

- **Module / subsystem**
- **Role in system**
- **Files loaded for context**
- **Why it matters for this review**
- **Primary risks**
- **Important assumptions**

### Rules

- Compress context; do not dump large file contents.
- Pull enough context to support judgment, not enough to overload the reviewer.
- If context remains incomplete, say what is still unknown.

---

## Phase 2 — Decompose the Change into Review Chunks

Do not review file-by-file by default. Review by meaningful chunk.

Good chunking dimensions:

- subsystem or module
- change intent
- architectural boundary
- execution path
- data flow
- risk class
- API / contract surface

### Good Chunk Examples

- auth token rotation core logic
- session middleware integration
- schema migration and compatibility handling
- API handler behavior changes
- test harness updates for new edge cases

### Avoid

Bad chunking patterns:

- arbitrary file-count buckets
- one chunk per file when the files are tightly coupled
- one giant chunk for the whole PR
- mixing cleanup with correctness-critical logic

### Required Output: Chunk Plan

Produce 3–8 chunks where possible. Each chunk should include:

- **Chunk name**
- **Files**
- **Intent**
- **Why review this separately**
- **Primary review lenses**
- **Potential failure modes**
- **Recommended review order position**

### Rules

- If the PR is mixed, explicitly separate unrelated concerns.
- Attach tests to the relevant chunk rather than isolating all tests at the end unless they truly stand alone.
- Attach docs/config to the chunk they clarify.

---

## Phase 3 — Guided Review, One Chunk at a Time

Review each chunk in a structured rhythm.

For every chunk, produce the following sections.

### 1. What Changed

Explain the actual change in plain language.

Include, where relevant:

- renamed or replaced abstractions
- control-flow changes
- validation changes
- persistence or state changes
- interface changes
- test behavior changes

### 2. Relevant Context

Explain what surrounding code or contract matters to understanding this chunk.

Include:

- prior behavior
- dependencies
- assumptions
- invariants
- lifecycle or state model
- compatibility constraints

### 3. What to Inspect

Give the reviewer a focused checklist for this chunk.

Examples:

- does this preserve previous error semantics?
- is state updated atomically?
- are all call sites migrated?
- are null / empty / concurrent paths covered?
- does the test prove the intended guarantee?

### 4. Potential Concerns

List candidate issues with evidence and uncertainty level.

Separate:

- **Observed fact**
- **Inference**
- **Risk hypothesis**

Do not overstate speculative concerns.

### 5. Questions for the Reviewer or Author

Ask the most useful questions, for example:

- Is the new invariant documented anywhere?
- Should this path fail closed rather than fail open?
- Are we intentionally changing compatibility here?
- Is this behavior relied on elsewhere?

### 6. Tentative AI Assessment

Offer a provisional judgment for the chunk:

- looks sound
- needs clarification
- likely non-blocking issue
- likely blocking issue

This remains provisional until the final consolidation.

### Rules

- Advance chunk by chunk, not all at once.
- Always make clear why this chunk matters.
- Prefer evidence-backed reasoning over generic critique.
- If a chunk is low-risk and straightforward, say so plainly.

# Review Lenses

Apply the lenses that matter for the current chunk. Do not mechanically force every lens onto every chunk.

## Correctness

Check:

- does the code do what the change claims?
- are success and failure paths both handled?
- are edge cases covered?
- are state transitions valid?
- are invariants preserved?
- are there ordering, partial-update, or race-condition risks?

## Security

Check:

- auth/authz implications
- trust boundaries
- unsafe input handling
- injection vectors
- secret handling
- privilege escalation risk
- insecure defaults
- replay or abuse scenarios in stateful flows

## Maintainability

Check:

- naming clarity
- local complexity
- duplicated logic
- abstraction quality
- readability of branching and state flow
- whether future maintainers can infer the real assumptions

## API / Contract Compatibility

Check:

- signature changes
- return-shape changes
- schema evolution
- backward compatibility
- migration completeness
- caller/callee alignment
- same API shape but changed semantics

## Performance

Check:

- unnecessary loops or duplicate work
- blocking operations in hot paths
- query explosion or N+1 patterns
- excessive serialization / allocation
- whether the correctness fix introduces a major cost

## Testing

Check:

- are the right codepaths tested?
- are edge cases tested?
- does the test assert the real contract or only incidental implementation details?
- are failure cases, retries, races, or rollback scenarios missing?

## Observability / Operations

Check when relevant:

- logging quality
- metrics/tracing continuity
- migration safety
- rollback feasibility
- deploy-order sensitivity
- feature-flag behavior

# Severity Rubric

Use a stable severity model so findings are easy to act on.

## Blocking

Must be fixed before merge.

Examples:

- likely correctness bug
- security flaw
- contract break without explicit intent
- unsafe migration
- missing critical error handling
- tests clearly insufficient for a risky behavioral change

## Should Fix

Not necessarily merge-blocking in all teams, but important enough to call out strongly.

Examples:

- meaningful maintainability regression
- ambiguous semantics in important codepaths
- risky but not yet proven edge-case gap
- important observability or rollback weakness

## Discuss

Needs clarification or design confirmation.

Examples:

- intentional behavior change not documented
- unclear compatibility expectations
- unclear ownership of new invariant
- test coverage may be sufficient, but confidence is low without explanation

## Nit

Minor cleanup or style suggestion.

Examples:

- naming tweaks
- comment clarity
- local simplification
- test readability improvements

## Praise

Explicit positive observations.

Examples:

- good isolation of concerns
- strong tests
- clear migration handling
- better failure semantics than before

# Comment Drafting

When the user wants actual review comments, convert findings into one of these forms.

## Inline Comment

Use when the issue maps to a specific line or local code region.

Format:

- what the concern is
- why it matters
- what alternative or question to consider

Example:

> This changes the refresh-token invalidation path, but I can't tell whether the old token can still be replayed if persistence succeeds after token issuance. Should this update be atomic or fail closed?

## Author Question

Use when intent is unclear and the review should not over-assert.

Example:

> Is the compatibility break here intentional? The old helper returned `null` on missing state, while this path now throws.

## Summary Comment

Use when you want to group findings from the whole review.

Structure:

- verdict
- blocking issues
- important non-blocking concerns
- questions
- positives

## Approval / Request-Changes Rationale

Tie verdict to severity:

- **Approve** — no blocking issues, at most minor should-fix / discuss items
- **Comment** — mostly questions, suggestions, or medium-confidence concerns
- **Request changes** — one or more blocking issues, or multiple serious should-fix concerns in risky codepaths

# Interactive Review Mode

When the workflow is interactive, stop at natural checkpoints.

After the review brief, ask implicitly through structure or explicitly through interaction whether to:

- inspect the highest-risk chunk first
- load more context for a module
- review all chunks in sequence
- draft comments now

After each chunk, the possible next moves are:

- go deeper on this chunk
- inspect a related file or caller/callee
- move to the next chunk
- draft a comment from this finding
- consolidate findings so far

If the workflow is non-interactive, preserve the same chunk rhythm in the written output anyway.

# Special Guidance for Reviewing AI-Generated Changes

This skill is especially useful for Claude Code, Codex, and other agent-generated changes.

Agent-written code often looks polished while hiding shallow understanding. Be extra alert for:

- plausible but wrong assumptions about system architecture
- partial migrations with missing call sites
- tests that prove only the happy path
- renamed abstractions that do not preserve semantics
- code that matches local style but violates deeper invariants
- “fake completeness” where config/docs/tests are updated just enough to look finished
- symptom fixes that do not preserve the underlying contract

### Extra Questions for Agent-Generated Changes

- Did the agent really understand the subsystem, or pattern-match nearby code?
- Are new abstractions semantically justified, or just cosmetically cleaner?
- Did it preserve non-obvious behavior relied on elsewhere?
- Are failure modes and rollback paths still safe?
- Are the updated tests validating the contract, or just the new implementation?

Do not reward fluency over correctness.

# Common Pitfalls

1. **Judging before understanding intent**
   - A strange-looking implementation may be correct under hidden constraints. Frame the change first.

2. **Reviewing only the diff**
   - Many bugs are visible only with surrounding code, callers/callees, or tests.

3. **Mixing unrelated concerns**
   - Large PRs often combine core logic, cleanup, tests, docs, and config. Split them.

4. **Applying every lens equally**
   - A test-only chunk does not need the same performance scrutiny as a hot-path change.

5. **Overstating speculative concerns**
   - Distinguish facts from suspicions. Label uncertainty.

6. **Letting AI replace the reviewer**
   - The goal is guided judgment, not blind acceptance of a one-shot summary.

7. **Trusting agent-generated code because it looks polished**
   - Fluent code can still be structurally wrong.

8. **Ignoring tests during context bootstrap**
   - Tests often reveal the intended contract more clearly than implementation code.

9. **Writing one giant final summary with no chunk structure**
   - That recreates the very problem this skill exists to solve.

# Verification Checklist

Before concluding the review, confirm:

- [ ] The review target was clearly identified
- [ ] The probable intent was stated and uncertainty labeled
- [ ] Relevant surrounding context was loaded
- [ ] Changes were decomposed into meaningful chunks
- [ ] Each chunk was reviewed with appropriate lenses
- [ ] Facts, inferences, and risk hypotheses were kept distinct
- [ ] Blocking issues were separated from non-blocking concerns
- [ ] Questions for the author were made explicit
- [ ] The final verdict reflects both findings and remaining uncertainty
- [ ] The reviewer was guided, not drowned in a diff dump

# One-Shot Recipes

## Recipe: Review a Large Mixed PR

1. Build the review brief from title, body, diff stats, and changed files.
2. Group files into logical chunks by subsystem and intent.
3. Load context for the highest-risk chunk first.
4. Review chunks in this order:
   - correctness-critical core logic
   - integration boundaries
   - persistence/schema changes
   - tests
   - cleanup/docs
5. Consolidate findings into blocking / should-fix / discuss / praise.

## Recipe: Review an Agent-Written Refactor

1. Infer the claimed refactor goal.
2. Compare old vs new abstraction boundaries.
3. Read callers and tests, not just changed functions.
4. Check for semantic drift and partial migration.
5. Look for preserved names with changed meaning.
6. Produce a final summary emphasizing contract preservation and missing edge cases.

## Recipe: Review an Unfamiliar Module

1. Start with context cards, not findings.
2. Read key interfaces and tests before implementation details.
3. Use chunking to keep scope bounded.
4. Prefer questions and tentative assessments over overconfident verdicts.
5. Mark uncertainty clearly in the final output.
