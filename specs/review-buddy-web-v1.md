# Review Buddy V1 Spec (Local Web App)

## Status

Draft for discussion.

## Product name

**Review Buddy**

The project name and the skill name stay the same. This spec describes the **local web app form factor** of Review Buddy. The product family, repository identity, and skill identity all remain **Review Buddy**.

---

## 1. Summary

Review Buddy is a local, human-in-the-loop code review interface designed for reviewing AI-generated or otherwise hard-to-parse code changes. In V1 it is delivered as a local web app. It combines a diff viewer, AI explanations, and structured reviewer commenting in a single local web page.

The first version focuses on one specific outcome:

> A reviewer can open a local web page, inspect a code diff, read AI guidance alongside the diff, leave comments easily, send those comments back to the AI, and receive follow-up explanations or structured review feedback.

A key V1 requirement is that Review Buddy is **agent-invocable**. A user should be able to ask the agent, in natural language, to use Review Buddy to review the current project changes, a repository branch diff, or a selected commit range. In response, the agent should prepare the review session and launch the local Review Buddy interface for interactive continuation.

This is not a generic code host, not a GitHub replacement, and not a one-shot auto-review bot. It is a guided review surface that helps a human understand, question, and judge code changes — especially code produced by AI coding agents.

---

## 2. Problem statement

As more code is written by AI, reviewers face a growing mismatch:

- the volume of changed code increases
- the polish of generated code makes it look more trustworthy than it may be
- reviewers have less patience for reading raw diffs line by line
- existing review tools assume the human can reconstruct intent, architecture, and risk directly from the diff

That assumption increasingly fails.

The real pain is not only “I need AI to review code for me.”
The real pain is:

> “I need help understanding and interrogating this diff without giving up control of the review.”

Review Buddy addresses this by making code review interactive:

- the AI explains the code and highlights risk
- the human comments on specific lines or chunks
- those comments go back to the AI
- the AI responds, clarifies, restructures, and helps draft a better review

---

## 3. Product goal

### Primary goal

Enable a reviewer to complete an interactive local review session on a diff through a web page.

### V1 success criteria

A user can:

1. Ask the agent to use Review Buddy for the current project changes, a branch comparison, a commit range, or a pasted unified diff.
2. Have the agent prepare and launch a Review Buddy browser page for that review target.
3. View the diff in the browser.
4. See AI-generated review guidance for the current review scope.
5. Add comments to a code range or to a logical review chunk.
6. Send those comments to the AI and receive a follow-up response.
7. Export the accumulated review output in a reusable format.

---

## 4. Non-goals for V1

The following are explicitly out of scope for the first version:

- direct GitHub/GitLab review comment publishing
- multi-user collaborative reviewing
- authentication / hosted deployment / cloud sync
- full IDE integration
- replacing git or code hosting platforms
- fully autonomous approval / rejection without human interaction
- broad code intelligence such as symbol graph navigation across huge repos
- polished enterprise workflow features such as permissions, audit trails, or notifications

These may come later, but they should not shape V1 architecture in a way that slows down the first useful version.

---

## 5. Target user

### Primary user

A human reviewer who needs to review:

- AI-generated changes
- large or mixed diffs
- unfamiliar subsystems
- changes where raw diff reading alone is too cognitively expensive

### Typical situations

- reviewing local branch changes before opening a PR
- reviewing a PR-like diff in a local clone
- reviewing changes generated by Claude Code, Codex, or other coding agents
- reviewing a refactor where the code is readable but intent is unclear

### Core user need

The user does **not** want the AI to replace their judgment.
The user wants the AI to:

- explain
- orient
- decompose
- challenge
- structure
- and help draft review feedback

while leaving the final decision to the human.

## 6. Design principles

### 6.1 Human-in-the-loop by default

The reviewer remains the decision-maker. AI output is guidance, not the final verdict.

### 6.2 Explanation before judgment

The system should help the reviewer understand the change before asking them to assess it.

### 6.3 Review by chunk, not only by file

The product should prefer meaningful review units over raw file ordering when possible.

### 6.4 Comments are first-class

The act of questioning, annotating, and sending feedback back to the AI is central to the workflow, not an afterthought.

### 6.5 Local-first

The default workflow should work entirely from a local repo and a local web server.

### 6.6 Structured outputs over prose blobs

Even when the UI shows natural language, the underlying review objects should be structured enough to support export, filtering, and later integrations.

### 6.7 Core-object-first design

All product, UX, storage, and protocol decisions should be organized around a stable set of core review objects and their relationships. UI panes, exports, and AI operations should all be explainable in terms of those objects.

### 6.8 Agent-first invocation

The primary entrypoint for Review Buddy V1 is the agent. Users should not need to manually open the web app first. Natural-language requests to review the current project, a target repository, a branch diff, or a commit range should trigger Review Buddy session preparation and local UI launch.

## 7. Core object relationships

Everything in Review Buddy should revolve around a small set of core objects.

### 7.1 Primary relationship model

- A `ReviewSession` contains the review state for one diff snapshot.
- A `ReviewSession` contains multiple `DiffFile` records.
- A `DiffFile` contains one or more `DiffHunk` records.
- A `ReviewChunk` groups one or more `DiffHunk` records into a meaningful review unit.
- A `CommentThread` belongs to a `ReviewSession` and is scoped to either a `DiffHunk`, a `ReviewChunk`, or the whole session.
- A `Comment` belongs to a `CommentThread`.
- A `Comment` may be written by the reviewer or by the AI.
- An `AIMessage` may describe a session, a chunk, or a reply inside a comment thread.
- A `SummaryFinding` belongs to a `ReviewSession` and may reference the chunk, hunk, or thread that produced it.

### 7.2 Product implication

This relationship model is the backbone of the product:

- the left pane navigates sessions, chunks, files, and threads
- the center pane renders files and hunks
- the right pane renders AI guidance, structured discussion threads, and summary state
- exports serialize the same objects into markdown and JSON artifacts
- AI operations consume and produce updates to these same objects

The system should avoid introducing UI-only concepts that cannot be mapped back to the core object model.

---

## 8. Core use case

A reviewer asks the agent to use Review Buddy for a local diff, a branch diff, or a selected commit range.

The system:

1. resolves the review target
2. loads or constructs the diff snapshot
3. creates a `ReviewSession`
4. generates an initial review brief
5. groups or attempts to group the diff into logical chunks
6. launches the local Review Buddy interface
7. shows the current diff and the AI explanation side by side
8. lets the reviewer add inline or chunk comments
9. sends reviewer comments back to the AI
10. receives follow-up AI responses and suggested review wording
11. accumulates findings into a final review summary

## 9. User experience flow

### Step 0: Agent invocation

The primary launch path starts inside the agent.

Typical user requests include:

- “用 review-buddy 帮我 review 当前项目的改动”
- “review 这个分支相对 main 的变更”
- “review 这几个 commit”
- “用 review-buddy 看一下这个仓库最近几次提交”

The agent should recognize these as Review Buddy requests and transition into session preparation rather than responding with only a textual summary.

### Step 1: Resolve review target

The agent identifies the requested review scope.

V1 supported sources:

- current working tree vs HEAD
- staged diff
- branch diff (e.g. `main...feature`)
- commit range diff
- pasted unified diff text

The system may also support a specified repository path as long as the target diff source can be resolved locally.

### Step 2: Prepare and launch session

Before the user enters the web UI, the system should:

- resolve the diff source
- normalize the diff
- create a `ReviewSession`
- generate a review brief
- generate chunk candidates
- launch the local Review Buddy page bound to that session

This launch step is part of the product requirement, not an optional convenience.

### Step 3: Orient the reviewer

Before deep inspection, the app shows a **Review Brief** generated by AI.

The brief includes:

- change type
- scope
- probable intent
- risk hotspots
- suggested review order
- confidence in inferred intent

This gives the reviewer a mental model before reading detailed code.

### Step 4: Present review chunks

The app organizes the review into chunks where possible.

A chunk is a meaningful review unit, such as:

- token rotation logic
- middleware integration
- schema migration behavior
- test coverage updates

Each chunk has:

- a name
- related files/hunks
- intent
- risk/lenses
- review order

Chunking is a core product concept, but the chunk generation mechanism may be best-effort. If chunking is weak or incomplete, the app may fall back to file/hunk navigation while still preserving AI explanation and comment flow.

### Step 5: Review a chunk interactively

For the selected chunk, the app shows:

- the relevant diff
- AI explanation for the chunk
- existing reviewer comments and AI replies

The AI explanation should roughly map to the Review Buddy skill’s guided review pattern:

- what changed
- relevant context
- what to inspect
- potential concerns
- questions
- tentative assessment

### Step 6: Add comments

The reviewer can:

- select a line range and add an inline comment
- add a chunk-level comment
- add a session/global review note

The UI should make this low-friction.

### Step 7: Send comments back to AI

When the reviewer submits a comment, the app sends structured context to the AI, including:

- review/session id
- thread id
- chunk id if applicable
- file and line anchors if applicable
- the relevant diff hunk
- reviewer comment text
- prior thread context if available

The AI responds with one or more of:

- a direct answer or explanation
- a risk analysis
- a severity suggestion
- a better draft review comment
- a request to inspect adjacent context
- a recommendation for the next chunk

These interactions should be represented as structured **discussion threads**, not as a free-form general chat surface. The V1 interaction model is thread-based and review-scoped.

### Step 8: Consolidate findings

As the session progresses, the app accumulates findings into a final review summary.

The final summary should support at least these buckets:

- blocking
- should fix
- discuss
- nit
- praise
- remaining uncertainty

### Step 9: Export results

The reviewer can export the review session into reusable artifacts.

V1 export targets:

- markdown summary
- structured JSON including comments and AI responses
- PR-ready review summary / comment draft markdown

## 10. Information architecture

## 10.1 Main layout

A three-pane layout is the default V1 target, and each pane should map cleanly to the core object relationships.

### Left pane: navigation

Contains:

- review title / diff source
- review brief entry point
- chunk list
- file list
- thread/comment counts / unresolved indicators

### Center pane: diff viewer

Contains:

- current file/chunk diff
- line numbers
- visual change markers
- selection support for creating inline comments

V1 should prioritize a clean unified diff view. Split view can come later.

### Right pane: AI and discussion panel

Contains tabs or sections for:

- AI Guide
- Discussion Threads
- Summary

#### AI Guide

Shows the current AI explanation for the selected review scope.

#### Discussion Threads

Shows reviewer comments, AI responses, and draft review text inside scoped discussion threads. This pane should feel like a structured inspector with per-scope threads, not like an open-ended chat interface.

#### Summary

Shows accumulated findings and the current review verdict state.

## 11. Functional requirements

## 11.1 Review session creation

The system must support creating a local review session from a diff source.

Minimum V1 capabilities:

- choose diff mode: working tree / staged / branch / commit range / pasted unified diff
- generate stable review session id
- persist session state locally

## 11.2 Agent-triggered launch

The system must support Review Buddy invocation from the agent via natural-language review requests.

Minimum V1 behavior:

- detect Review Buddy intent from a user request
- resolve the requested review target
- prepare a `ReviewSession`
- launch the local web interface for that session
- return the user into a live interactive review surface rather than only a text summary

## 11.3 Diff ingestion

The system must ingest and normalize a diff into structured reviewable units.

The normalized model should preserve:

- file path
- file status (added/modified/deleted/renamed if available)
- hunks
- line mappings and anchors
- raw patch text

## 11.4 Review brief generation

The system must be able to generate an initial review brief for the session.

## 11.5 Chunk generation

The system should generate logical review chunks as a core part of the experience, while treating the chunk generation algorithm as best-effort.

Each chunk should include:

- chunk id
- chunk name
- related files/hunks
- intent summary
- primary review lenses
- risk notes
- ordering metadata

## 11.6 Diff viewing

The system must display code diffs in the browser.

Minimum V1 behavior:

- navigate by file and chunk
- show unified diff
- support line-range selection
- visually indicate comment thread anchors

## 11.7 AI explanation panel

The system must display AI-generated guidance for the current chunk or selected scope.

## 11.8 Comment creation

The system must support at least three comment scopes:

### Inline comment thread
Bound to a file and line range or hunk anchor.

### Chunk comment thread
Bound to a logical review chunk.

### Global/session thread
Bound to the overall review session.

Comments must live inside explicit discussion threads.

At minimum V1 should support:

- one thread anchored to a line range / hunk
- one thread anchored to a chunk
- one thread anchored to the overall review session

Each thread should support multiple messages over time, including reviewer comments, AI replies, and reviewer follow-ups.

## 11.9 AI feedback loop

The system must send reviewer comments and context back to the AI and store the response.

## 11.10 Summary accumulation

The system should allow findings to accumulate into structured severity buckets over time.

## 11.11 Export

The system must export the session in:

- markdown
- JSON
- PR-ready markdown drafts for review summary and comments

## 11.12 Thread lifecycle

Discussion threads are first-class workflow objects.

At minimum V1 should support the following lifecycle states:

- `open`
- `resolved`
- `dismissed`

### Creation rules

- A reviewer may create a new thread from a line-range selection.
- A reviewer may create a new thread from a chunk.
- A reviewer may create a new global/session thread.
- The AI may propose a concern, but V1 should treat AI-raised concerns as either:
  - an AI-authored message inside an already-created thread, or
  - a suggested draft for the reviewer to accept into a new thread.

To keep the workflow reviewer-led, V1 should avoid silently creating user-visible new threads without a clear trigger.

### Reuse rules

- If the reviewer interacts with an existing anchor that already has an open thread, the UI should prefer reopening or continuing that thread rather than silently creating a duplicate.
- The system may allow explicit “new thread anyway” behavior later, but the default should reduce duplicate thread sprawl.

### Resolution rules

- A reviewer can mark a thread `resolved`.
- A resolved thread can be reopened by a later reviewer or AI response if new information appears.
- A thread can be marked `dismissed` when the concern is judged invalid, obsolete, or intentionally not actionable.

### Visibility rules

- Open threads should be visually prioritized.
- Resolved and dismissed threads should remain accessible for auditability and context.

## 11.13 Finding lifecycle

Findings are structured review conclusions derived from one or more chunks or threads.

### Creation rules

- The AI may suggest candidate findings.
- The reviewer may create or promote a finding manually.
- V1 should preserve a distinction between:
  - candidate findings still under discussion
  - accepted findings included in the review summary

### Edit rules

- A finding should be editable before export.
- A finding should keep references to its originating chunk, hunk, or thread when possible.

### Promotion rules

Typical path:

1. thread discussion identifies a concern or positive observation
2. AI suggests a finding draft
3. reviewer accepts, edits, or rejects it
4. accepted finding appears in the structured summary

This prevents the final summary from being just a raw dump of thread text.

## 13. AI interaction model

The AI layer should be treated as a structured collaborator, not only a text generator.

### 13.1 Review-level AI tasks

- generate review brief
- generate chunk plan
- generate session summary

### 13.2 Chunk-level AI tasks

- explain current chunk
- identify review lenses and risks
- answer reviewer questions about the chunk

### 13.3 Comment-level AI tasks

- answer a reviewer comment
- suggest severity
- draft clearer review wording
- suggest what adjacent context to inspect next

Comment-level AI tasks should operate within explicit discussion threads rather than an unconstrained chat channel.

### 13.4 Finding-level AI tasks

- suggest candidate findings from thread activity
- draft concise finding titles and bodies
- recommend severity buckets
- identify duplicate or overlapping findings

### 13.5 Response style expectations

AI output should prefer:

- evidence-backed claims
- explicit uncertainty when inference is weak
- structured fields where possible
- concise explanations tied to the current diff scope

The AI should avoid pretending certainty when context is incomplete.

### 13.6 Boundary between `Comment` and `AIMessage`

To avoid overlap in the object model:

- `Comment` is the canonical message type **inside a discussion thread**.
- AI replies that appear inside a thread should be stored as `Comment(author="ai")`.
- `AIMessage` is reserved for AI-generated artifacts that are **not** ordinary thread messages, such as:
  - review brief
  - chunk explanation
  - summary update
  - finding suggestion payloads

This keeps thread conversations simple while preserving structured AI outputs outside the thread flow.

## 14. API / protocol shape

V1 does not need a public stable API, but the app should internally separate UI events from AI operations using structured requests and responses. Those requests and responses should map cleanly to the core object relationships.

### Example operation: generate review brief

Request:

```json
{
  "action": "generate_review_brief",
  "review_id": "r1"
}
```

Response:

```json
{
  "change_type": "feature",
  "scope": "6 files changed across auth and session handling",
  "probable_intent": "Reduce token refresh race conditions and simplify middleware state handling",
  "risk_hotspots": [
    "refresh token invalidation ordering",
    "session compatibility semantics"
  ],
  "suggested_review_order": ["chunk-1", "chunk-2", "chunk-3"],
  "confidence": "medium"
}
```

### Example operation: submit reviewer comment

Request:

```json
{
  "action": "submit_comment",
  "review_id": "r1",
  "thread_id": "thread-14",
  "chunk_id": "chunk-2",
  "anchor": {
    "file": "src/auth.ts",
    "start_line": 84,
    "end_line": 96
  },
  "comment": {
    "author": "reviewer",
    "body": "This token rotation path looks non-atomic. Could the old token still be replayed if persistence succeeds late?"
  }
}
```

Response:

```json
{
  "ai_response": "The risk appears real if issuance and invalidation are not coupled atomically. I would inspect the token store write semantics and any retry behavior.",
  "severity": "discuss",
  "suggested_draft": "Can we confirm this rotation is atomic? If invalidation can lag issuance, the old refresh token may remain replayable longer than intended.",
  "needs_more_context": true,
  "recommended_followups": [
    "inspect token store implementation",
    "inspect error path after new token issuance"
  ]
}
```

### Example operation: promote finding from thread

Request:

```json
{
  "action": "promote_finding",
  "review_id": "r1",
  "thread_id": "thread-14",
  "candidate": {
    "severity": "discuss",
    "title": "Token rotation atomicity is unclear",
    "body": "The current diff does not clearly guarantee that refresh token invalidation and issuance are atomic. If invalidation can lag issuance, replay risk may remain."
  }
}
```

Response:

```json
{
  "finding_id": "finding-7",
  "status": "accepted",
  "linked_thread_id": "thread-14"
}
```

## 15. UX requirements

### 15.1 Low-friction commenting

Adding a comment should be fast enough that reviewers actually use it.

### 15.2 Clear scope awareness

The UI should make it obvious whether the user is commenting on:

- a line range
- a chunk
- the whole review

### 15.3 Strong context retention

When a reviewer switches between chunks, the system should preserve the AI discussion history and comment history.

When a reviewer revisits an existing thread, the system should preserve the full thread state and clearly show thread scope.

### 15.4 Progressive disclosure

Do not overwhelm the user with all analysis at once. Let them focus on the current chunk while keeping summary state visible.

### 15.5 Exportable outcomes

The end of a review should feel like a concrete artifact was produced, not just a transient chat.

### 15.6 Thread clarity

The UI should make it obvious:

- which messages belong to which thread
- whether a thread is open, resolved, or dismissed
- which finding(s), if any, were derived from a thread

## 16. Local persistence

V1 should persist review state locally so that a session can be resumed.

At minimum, local persistence should cover:

- diff source metadata
- normalized diff data
- review brief
- chunk plan
- discussion threads
- comments
- AI replies
- summary findings
- final summary

Storage technology is an implementation detail and can be decided in the plan phase.

---

## 17. Security and privacy assumptions

V1 is local-first and should assume the code under review may be sensitive.

Implications:

- default behavior should operate on the local machine
- users should understand when diff contents are being sent to an LLM
- data should not require a hosted Review Buddy service

The exact provider/config mechanics belong to implementation planning, but the product behavior should make AI-bound operations legible to the user.

---

## 18. Observability for the reviewer

The system should expose enough session status to keep the reviewer oriented.

Useful V1 status indicators:

- current review source
- chunk count
- thread count
- comments count
- outstanding/open comments count
- candidate findings count
- accepted findings count
- last AI action
- export status

## 19. Risks and trade-offs

### 19.1 Chunk quality risk

Poor chunking could confuse rather than help. V1 should allow fallback navigation by file/hunk even if chunking exists.

### 19.2 Overly verbose AI risk

Too much prose will recreate the same cognitive overload as large diffs. AI output must stay scoped and structured.

### 19.3 Anchor instability risk

Diff line anchors can drift when the underlying working tree changes. V1 should assume a review session is tied to a snapshot of a diff.

### 19.4 False reviewer trust risk

If AI explanations are fluent but wrong, users may over-trust them. The UI and copy should reinforce that AI output is guidance.

### 19.5 Thread sprawl risk

If the system creates too many duplicate threads, the discussion surface becomes noisy and harder to use. Reuse and resolution behavior must be deliberate.

### 19.6 Summary drift risk

If findings are promoted automatically without reviewer oversight, the exported review may misrepresent reviewer intent. Candidate vs accepted finding states mitigate this risk.

## 20. Resolved product decisions

The following decisions are resolved for V1:

1. **Diff inputs:** V1 supports all planned input modes — working tree, staged, branch diff, commit range, and pasted unified diff.
2. **Chunking:** chunking is a core concept, while chunk generation itself is best-effort with fallback to file/hunk navigation.
3. **Thread model:** comments and AI replies must live in explicit discussion threads.
4. **Right pane behavior:** keep the current structured-inspector model; V1 does not expose a general-purpose chat mode.
5. **Exports:** V1 includes PR-ready markdown drafts in addition to markdown summary and JSON export.
6. **Naming:** product and skill remain Review Buddy; this spec is specifically for the local web app form factor.
7. **Architecture emphasis:** all design should revolve around the core object relationships.
8. **Thread representation:** thread-local AI replies are stored as `Comment(author="ai")`, while non-thread AI artifacts are stored as `AIMessage`.
9. **Finding workflow:** findings can be AI-suggested, but reviewer acceptance governs the final exported summary.
10. **Launch model:** Review Buddy is agent-invocable and should launch from natural-language review requests rather than requiring the user to open the UI manually first.

The following questions remain open for later clarification or implementation planning:

1. Should AI explanations be pre-generated for all chunks, or generated lazily when opened?
2. Should comments support explicit severity tagging by the reviewer in V1, or only by AI suggestion?
3. What amount of surrounding unchanged context should the diff viewer show by default?

---

## 21. Acceptance criteria for V1

Review Buddy V1 is successful if all of the following are true:

1. A user can ask the agent to use Review Buddy for the current project, a target branch diff, a commit range, or a pasted unified diff.
2. The app can resolve that request into a local review session and launch a browser-based review page.
3. The user can navigate the diff by file and, when available, by chunk.
4. The user can read AI-generated review guidance for the current scope.
5. The user can add inline and chunk-level comments, organized as explicit discussion threads.
6. The user can submit those comments to the AI and receive follow-up responses.
7. The user can resolve, dismiss, and reopen threads.
8. The user can promote, edit, accept, reject, and export findings.
9. The session state persists locally and can be resumed.
10. The review can be exported as markdown, PR-ready markdown drafts, and JSON.
